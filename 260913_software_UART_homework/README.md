#### 首先只考虑 Receiver 的架构。思考清楚前绝不动笔写代码。
- 想法：经过与 GPT 交流，确定“外部下降沿中断开启接收进程，计时器中断进行具体接收”的框架。此时需要留意：在接收过程中前者应当被禁止触发（我的想法是物理层面上不被触发）
- 想法： Handling 不应该占用时间太长（因为第一个字节发送完成后第二个字节紧接着就会来）——不过通过flag请求中断？这不是又要引入第三个中断了吗？——看来需要其级别更低，或者直接在main中完成
- 想法：需要复刻每个bit“三中取二”以及进入start bit之后的再次检测
- 不需要对应原RI中断的中断——因为CPU处理传入的字节并不需要硬件动作或者严格的时间规定（一定要在收到字节后若干微秒内完成处理）——原来有中断是因为UART硬件模块与CPU是分开的
- 暂时不引入缓冲机制，在CPU没有消费完旧数据时直接丢弃——我们要求 Handling 必须足够快。（以后要加缓冲区也要加在main中或者说调用软件UART服务的程序中）

#### 然后考虑 Transmitter

- 小特性是，最初上电时软件UART会收到一长串的随机的字节，这应该是由最开始的噪声导致的。这启发我们，在实际运用UART的时候（可能只包括软件UART），需要设置一定等待时间以忽略上电初期的杂乱噪声信号，避免其对主要逻辑造成干扰。当然，本项目或者说我写好的`UART_Receiver`模块不会做这一项处理，而本项目main中的代码会忠实地反映这一现象。当然从软件工程角度，这一模块的利用者应该自己在外部逻辑中实现“忽略噪声”的代码。

- 考虑到独立维护一个`sample_phase = 0, 1, 2`生成的汇编代码可能远少于使用`DIV AB`及相关指令的汇编代码（即使后者改成只运行一次指令并且复用），我先需要添加`sample_phase`（实际上是GPT的建议）；

- 写的过程中发现还需要加一个`is_end_checking`
- 启示：正是因为上述除法-取余、多位位移动等指令过重，在ISR等实时性要求苛刻的场景下占用时钟周期太多，所以我们要从源头上避免维护一个“需要现场除法计算”的状态变量。
- 第三次实验：对于单个Byte大成功！所有我尝试的单个字节都成功返回了。
- 对于多个字节：我多次传入的`0x114514`，单片机没有返回最后一个字节——但是数码管最高字节每次都在加1。这大概率说明，Receiver已经接到了最后一个`0x14`，但是没有成功写入。接下来是继续对代码根据汇编做实时性优化，还是让外部在利用该模块的时候使用缓冲区，还有待决策。
- 对于`0x11 45 14 19 19 81 00`，典型行为是单片机接到`0x 11 45 81`（数码管显示），并且数码管最高位增加4（确实是未成功处理4个字节）。同时，通过Transmitter传回的数据却并不一定是`0x 11 45 81`了（也就是Transmitter此时反倒出现了一定程度的失真）。需要注意的是，这一条描述的是典型行为而不是所有行为。单片机并不一定接到`0x 11 45 81`甚至不一定接到3个字节 out of 7。我这里进行得很快所以没有记录所有行为。
- 对于Receiver的EndChecking引入超时机制（GPT提到的）似乎是不必要的。对于PC通过STC-ISP软件一次连续发送多个字节的默认设置（不是自动重复），Receiver似乎能真正把所有字节都接到，只是有的字节会被丢弃。这意味着，关键还是在于外部利用者的优化。
