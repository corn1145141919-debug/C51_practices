### 9月14日
- 想法：硬件方面的架构不同决定了我绝对不会一板一眼地复刻原硬件 UART 的逻辑流程。
#### 首先只考虑 Receiver 的架构。思考清楚前绝不动笔写代码。
- 想法：经过与 GPT 交流，确定“外部下降沿中断开启接收进程，计时器中断进行具体接收”的框架。此时需要留意：在接收过程中前者应当被禁止触发（我的想法是物理层面上不被触发）
- 想法： Handling 不应该占用时间太长（因为第一个字节发送完成后第二个字节紧接着就会来）——不过通过flag请求中断？这不是又要引入第三个中断了吗？——看来需要其级别更低，或者直接在main中完成
- 想法：需要复刻每个bit“三中取二”以及进入start bit之后的再次检测
- 不需要对应原RI中断的中断——因为CPU处理传入的字节并不需要硬件动作或者严格的时间规定（一定要在收到字节后若干微秒内完成处理）——原来有中断是因为UART硬件模块与CPU是分开的
- 暂时不引入缓冲机制，在CPU没有消费完旧数据时直接丢弃——我们要求 Handling 必须足够快。（以后要加缓冲区也要加在main中或者说调用软件UART服务的程序中）

#### 然后考虑 Transmitter
- 想法：原来的程序中甚至没有引入中断。这意味着我们只需要自动重装计时器的计时器中断
- 问题：收发相位可能不同。但是数码管已经占用了Timer0，因此我只能使用Timer1的信号，同时修改TX和RX端自己对信号的计数和解释
- 原版$16 \times 9600 \mathrm{Hz}$实在太快，可能塞不下几个时钟周期，无法执行完整的ISR。那么，我们需要从多个角度提高单个 tick 内可以塞进去的 CPU 时钟周期数。一方面，给CPU提高到6T（双倍速，烧录时决定）；另一方面，降低采样频率。
——取舍：采样频率低则误判错判概率高；采样频率高则CPU无法正确执行完整所有指令。
- 嵌入式开发，既需要考虑正确性也需要考虑时间限制
- 实时性分析：需要看代码需要多长的时钟周期——看WCET；看反编译结果
- 先按$3 \times 9600\mathrm{Hz}$写，然后再进行分析

### 10月4日（真是隔了好长时间啊）

- 补充：不仅计时器中断要确保自己运行期间下降沿中断被禁止，而且下降沿中断和计时器中断自己也要控制计时器中断是被激活还是被禁止
- 补充一下关于 Handling 的说法：所谓 Handling 只是把数据发送出去（即发送到类似原架构中读SBUF的地方）
- 原版硬件uart的行为具体是怎样——似乎是在RI没有恢复0的时候丢弃（不是一开始而是完整走完接受流程后丢弃）
- 对于这台机器来说，维持内部的情况 vs 具体地接收信息 vs 处理接收到的信息本就是“三个”需要并行的任务，而在原生硬件uart中，具体地接受信息的部分又被硬件包揽了，因此处理接收到的信息可以用单独的中断，不怕打断硬件信息接收；但是在我们的项目中，三个任务需要抢同一个cpu，因此我们可能要用更低级的中断或者干脆进一步降级为super loop中固定的一步——或者说时间上来得及就不用特别加低级中断了？

### 10月6日
- 优先级安排：RX相关先于TX相关，TX相关先于数码管相关（因为接收必须比发送有更可靠的实时性。假如发送失败，以后可以在main代表的上层写失败处理代码，重试发送；假如接收失败，那么就永远追不回来了。或者说发送往后相位上错一点代价比接收相位错一点代价小得多。
